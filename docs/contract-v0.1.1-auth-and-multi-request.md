# 碰个面 MVP 增量契约 contract v0.1.1

> 状态：已确认
> 生效日期：2026 年 9 月 17 日
> 依赖契约：`contract-v0.1.md`
> 适用范围：全局身份入口、多需求关系与并发边界

## 1. 目的与兼容性

本文件补充 `contract-v0.1.md`，不替换原契约，不改变已冻结的数据库主表、状态机和 API 返回结构。

以下成果继续有效，无需返工：

- 注册、登录、`GET /api/v1/me` 和 JWT 鉴权。
- 需求、匹配批次、候选人、邀请、成局和成员数据结构。
- 邀请接受、拒绝、超时、候补递补、通知、签到、评价和复组流程。
- `/me/requests`、`/me/invitations`、`/me/sessions` 等现有接口。

合作成员可以继续按 `contract-v0.1.md` 开发履约和通知。本增量由全局 H5 入口和发起人侧实现吸收。

## 2. 全局身份入口

### 2.1 页面边界

- 注册和登录属于产品全局能力，不属于数学建模或任何具体竞赛。
- 公开介绍页可以匿名访问；进入发现、匹配、发布、邀请、成局、历史和个人中心等业务工作台前必须登录。
- 当前 H5 没有独立公开介绍页时，根页面直接展示全局注册或登录页。
- 登录后所有业务页面共享同一当前用户和 JWT，不得在具体竞赛页面再次要求输入手机号和密码。
- 具体竞赛页面只能读取全局身份，不得自行维护第二套用户、token 或退出状态。

### 2.2 会话恢复

- H5 启动时读取已有 JWT，并调用 `GET /api/v1/me` 验证和恢复当前用户。
- 恢复完成前不得以默认用户或硬编码用户进入业务工作台。
- JWT 无效或用户不是 `ACTIVE` 时，清除本地凭证并回到全局登录页。
- 网络错误与身份失效必须区分：网络错误允许重试，不得直接删除仍可能有效的凭证。
- 登录、注册和退出在同一浏览器的多个标签页之间同步。

### 2.3 前端职责

- 全局认证状态至少包含：`status`、`user`、`accessToken`、`error`。
- 全局认证层统一提供注册、登录、恢复、重试和退出能力。
- API 收到已登录请求的 `401` 后，统一使全局会话失效。
- 工作台顶部展示当前用户，提供明确的退出入口。
- LocalStorage 只允许保存 P0 JWT 和非事实型界面偏好，不得保存邀请、成局、签到等业务事实。

### 2.4 接口保持不变

继续使用：

- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `GET /api/v1/me`
- `Authorization: Bearer <token>`

本增量不修改上述接口的请求体、响应体和 JWT 载荷。

## 3. 多需求与成局关系

### 3.1 基本关系

- 一个用户可以创建多条需求，历史需求数量不设上限。
- 一条需求只能有一个创建者。
- 一条需求最多对应一个 `session`；首轮有效邀请产生 `FORMING` 成局。
- 一条需求可以产生多条主选或候补邀请。
- 用户可以同时作为自己需求的发起人和其他需求的受邀人，但必须通过时间冲突检查。
- “创建需求”不等于“直接成局”；只有角色空位满足后，成局才转为 `CONFIRMED`。

### 3.2 发起权限与数量

- `ACTIVE` 用户可以发布本人需求；服务端始终从 JWT 读取创建者和学校。
- 每个用户同时最多拥有 3 条活动需求。
- 活动需求状态包括：`DRAFT`、`OPEN`、`MATCHING`、`INVITING`。
- `FULFILLED`、`CANCELLED` 和 `EXPIRED` 不计入活动需求上限。
- 相同创建者、场景、竞赛名称和起止时间的非终态需求视为重复需求，必须拒绝。
- 同一创建者不得发布启动会时间重叠的活动需求。
- `POST /api/v1/requests` 必须使用幂等键，重复提交不得新增第二条需求。

### 3.3 邀请边界

- P0 邀请只来自当前匹配批次，普通用户不能搜索任意用户并点名邀请。
- 每条需求独立匹配、独立邀请、独立成局，不得复用其他需求的候选人或邀请状态。
- 同一用户可以收到多条时间不冲突的邀请。
- 接受邀请时，服务端必须再次检查已确认成局和其他已接受邀请的时间冲突。
- 接受成功后，服务端取消该用户其他时间重叠的 `PENDING` 或 `QUEUED` 邀请，并写入状态事件。
- 前端提示不代替服务端事务、锁和数据库约束。

## 4. H5 页面归属

登录后的全局工作台至少包含以下入口：

- 发现与搜索。
- 发起组队。
- 我的需求。
- 我的邀请。
- 我的成局与历史。
- 站内通知。
- 个人资料与退出登录。

数学建模发布页只负责提交需求和显示该需求的匹配结果。它不得承担登录、注册、账号切换或全局会话恢复。

## 5. 分工边界

### 全局入口与发起人侧

- 实现全局登录、注册、恢复、退出和 `401` 处理。
- 从数学建模页面移除内嵌登录。
- 实现多需求发布、列表、详情、取消和冲突保护。

### 邀请、成局与履约侧

- 继续实现邀请回应、候补递补、成局、通知、签到、评价和复组。
- 业务页面在集成时读取全局认证上下文，不需要重写已有服务端接口。

## 6. 增量验收

- [ ] 未登录访问业务工作台时只出现全局注册或登录入口。
- [ ] 登录一次后，数学建模页面不再出现手机号和密码输入框。
- [ ] 刷新页面后通过 `/me` 恢复同一真实用户。
- [ ] 无效 JWT 自动回到登录页；临时网络错误保留重试能力。
- [ ] 工作台顶部显示当前用户并可退出。
- [ ] 原有登录、需求、邀请、成局和履约接口结构没有变化。
- [ ] 同一用户可以查看多条历史需求，每条需求保持独立状态。
- [ ] 活动需求上限、重复发布、幂等和时间冲突由服务端执行。
- [ ] 合作成员当前分支不需要因本增量重写数据库或履约接口。
